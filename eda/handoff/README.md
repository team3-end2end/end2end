# EDA 인계서 — NYC Yellow Taxi 결제수단 예측

**작성일** 2026-08-05 · **데이터** `data/raw/yellow_tripdata_2026-05.parquet` (4,090,836건 × 20항목)
**Target** `payment_type` (분류) · **양식** Question / Analysis / Next Action (강의자료 p31–32)

---

## TL;DR

- 데이터는 건강하다. 극단값 몇 개만 잡으면 그대로 쓸 수 있다.
- **`tip_amount`·`total_amount`는 빼라** — 현금은 팁이 0으로 기록돼 정답을 그대로 알려준다.
- **`payment_type=0` 95만 건은 지우지 마라** — 결측이 아니라 요금을 항목별로 안 쪼갠 것. 지우면 장거리 운행이 통째로 사라진다.
- **70달러 정액 9.8만 건도 지우지 마라** — 오류가 아니라 JFK 공항 요금제다.
- **이상치를 걷어내기 전 상관계수는 믿지 마라** — 30만 마일 값 하나로 거리↔요금이 0.008이 된다 (실제 0.866).
- **거리·요금은 로그 변환하라** — 한쪽에 심하게 쏠려 있고, 변환하면 종 모양이 된다.
- **지역 259종은 원핫 대신 타겟/빈도 인코딩하라** — 컬럼이 폭발한다.
- **승·하차 시각으로 이동시간·시간대·요일을 만들어라** — 시간대가 결제수단을 잘 가른다.
- 사업자·시간대는 앱선불을 잘 가르지만, **카드 vs 현금은 지역 말고 쓸 만한 신호가 없다.**
- **3분류 정확도가 높아도 그건 쉬운 쪽(앱선불)에서 번 점수다** — 클래스별로 평가하라.
- **확인 요청:** `payment_type=0`·`RatecodeID=99`의 공식 정의, 그리고 목표를 2분류로 할지 3분류로 할지.

## 변수 유용성

| 변수 | 카드 vs 현금 | 앱선불 구분 | 조치 |
|---|---|---|---|
| VendorID | 약함 | **매우 강함** (V6=100%, V7=0%) — 단, 아래 주의 | 원핫 인코딩 |
| PULocationID | **강함** (지역별 현금 0~77%) | 중간 | 타겟 인코딩 또는 구간화 |
| 시간대·요일 | 미확인 | **강함** (새벽4시 51% ↔ 낮 16%) | 파생변수 생성 |
| fare_amount / trip_distance | **약함** (분포 겹침) | 중간 | 유지하되 기대 낮춤 |
| tip_amount / total_amount | — | — | ⛔ 제외 |

> **⚠️ VendorID 주의 — 누수는 아니지만 동어반복 위험.** `payment_type=0`은 "결제수단을 항목별로 보고하지 않음"이고, Vendor 6은 원래 항목을 분리 보고하지 않는 사업자다. 즉 "안 적는 회사라서 안 적혀 있다"는 순환 논리라 맞혀도 얻는 정보가 없다. 사업자는 예측 시점에 알 수 있는 정보이므로 **변수는 유지**하되(Vendor 6·7은 합쳐 1.5%뿐), 성능이 사업자에 과도하게 의존하면 **사업자 제외 후 재학습해 비교**할 것.

> **두 과제는 난이도가 다르다.** 3분류로 학습하면 전체 정확도는 높게 나오되 그 성능은 대부분 "앱선불 맞히기"에서 나온 것 — **클래스별 지표로 평가해야 한다.** (강의 p8: "정확도는 높은데 재현율이 낮으면 모델이 활용 가능한가?")
