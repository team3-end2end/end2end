# 데이터 준비 결과 리포트 — NYC Yellow Taxi 결제수단(payment_type) 예측

`data_preparation.ipynb` 실행 결과를 바탕으로 작성. 코드·수치는 해당 노트북에서 재현 가능.

---

## TL;DR

- 원본 4,090,836행 × 20열 → 필터링 후 **3,891,255행**(95.12% 유지) → 최종 피처 테이블 **12열**(피처 11 + 타깃 1)
- 타깃은 3-클래스: **신용카드 68.36% · Flex Fare 22.57% · 현금 9.07%** (무료·분쟁은 표본 부족으로 제외)
- **제외한 컬럼 10개**는 전부 `payment_type`과 구조적으로 얽힌 누수 컬럼이거나(`passenger_count` 등 5개 + `tip_amount`·`total_amount`·`extra`) 저분산 컬럼(`mta_tax`·`improvement_surcharge`) — 근거는 아래 2번 표
- **중복 제거는 반드시 컬럼을 줄이기 전에 해야 함** — 순서를 반대로 하면 서로 다른 트립이 "중복"으로 잘못 잡혀 0건→16,306건으로 급증하는 문제를 겪음
- 새 컬럼이 생겨도 조용히 넘어가지 않도록 **미검토 컬럼 경고 로직**을 최종 선택 단계에 넣어둠
- **`is_airport`, `hour`, `day_of_week` 파생 컬럼 추가** — 생성 이유는 "파생변수 생성 이유" 표 참고
- **아직 미반영 다음 작업자가 검토할 부분**: 3번 표 참고

## 1. 사용하는 컬럼

| 컬럼 | 구분 | 비고 |
|---|---|---|
| `trip_distance` | 수치형 피처 | `>0` 이면서 `<200` 필터링됨 |
| `fare_amount` | 수치형 피처 | 팁 미포함(미터기 시간·거리 요금만), `>0` 필터링됨 |
| `trip_duration` | 수치형 피처 (파생) | `tpep_dropoff_datetime - tpep_pickup_datetime`(분), `0~180` 범위만 유지 |
| `cbd_congestion_fee` | 수치형 피처 | 맨해튼 혼잡구역(CBD) 통과 여부에 따른 정액 부과금(\$0/\$0.75). 결제수단과 무관한 위치 기반 값이라 포함 |
| `tolls_amount` | 수치형 피처 | 통행료. 결제수단별 0-비율 차이가 92.5~95.2%로 미미해 안전하다고 판단, 포함 |
| `PULocationID` | 범주형 피처 | 승차 구역 코드 |
| `DOLocationID` | 범주형 피처 | 하차 구역 코드 |
| `hour` | 범주형 피처 (파생) | `tpep_pickup_datetime`의 시(0~23) |
| `day_of_week` | 범주형 피처 (파생) | `tpep_pickup_datetime`의 요일(0~6) |
| `VendorID` | 범주형 피처 | 4종(1,2,6,7). V6·V7은 표본이 적어 해석 주의 (아래 3번 참고) |
| `is_airport` | 범주형 피처 (파생, 이진) | 공항(1) · 그 외(0). `PULocationID`/`DOLocationID` ∈ {132(JFK), 138(LaGuardia), 1(Newark)}이면 1 (전체의 8.01%) |
| `payment_label` | **타깃** (파생) | `payment_type`을 문자열로 매핑: 0=Flex Fare, 1=신용카드, 2=현금 |

**행 필터링 단계별 상세** (순서대로 적용, 원본 4,090,836건 기준):

| 필터 | 적용 전 | 적용 후 | 제거 건수 | 비고 |
|---|---|---|---|---|
| `fare_amount > 0` | 4,090,836 | 4,073,654 | 17,182 | 요금 0 이하는 취소/오류 건으로 판단. 상한 없음 — 캡을 걸어도 상관계수(0.86대 유지)·스케일링 왜곡 감소 효과가 없고, 오히려 정상 장거리 요금(최대 \$881)만 잘려나감 |
| `trip_distance > 0` | 4,073,654 | 3,962,811 | 110,843 | 0마일인데 평균 \$30 요금 부과 → 미터기/GPS 오류 |
| `trip_distance < 200` | 3,962,811 | 3,962,738 | 73 | 레버리지 극단값 제거. 자체 검증: 이 필터 없이는 `trip_distance`↔`fare_amount` 상관계수가 0.008로 왜곡됨, 적용 시 0.86대로 안정화 (원본 최댓값 307,491마일은 정상권 99%ile의 15,793배) |
| `~(fare_amount≥$100 & trip_distance<1)` | 3,962,738 | 3,962,189 | 549 | 요금-거리 불일치 제거. 대부분 `RatecodeID=5`(협상요금)이면서 거리가 1마일 미만인데 요금은 \$100 이상 — 미터기/GPS 기록 오류로 판단. **제거 시 상관계수가 0.8623→0.8675로 오히려 개선**되어 정상 신호가 아님을 뒷받침 |
| `payment_type in {0,1,2}` | 3,962,189 | 3,942,906 | 19,283 | 3-클래스 타깃만 유지 (무료·분쟁 제외) |
| `tpep_pickup_datetime`이 2026-05 범위 내 | 3,942,906 | 3,942,892 | 14 | 수집 기간(2026-05) 밖 이상값 |
| `0 < trip_duration < 180(분)` | 3,942,892 | 3,891,255 | 51,637 | 0분 이하(기록 오류)·3시간 초과(장기 방치/오류로 판단) 제거 |

**파생변수 생성 이유**: 원본 컬럼을 그대로 안 쓰고 새로 만든 컬럼들의 근거. 형식(값 범위 등)은 1번 표 참고.

| 파생변수 | 원본 컬럼 | 생성 이유 |
|---|---|---|
| `trip_duration` | `tpep_pickup_datetime`, `tpep_dropoff_datetime` | 원본에 운행 소요시간을 직접 나타내는 컬럼이 없어 하차-승차 시간 차이(분)로 계산 |
| `hour` | `tpep_pickup_datetime` | 원본 datetime은 값이 거의 다 달라 모델이 학습할 반복 패턴이 없음 → 반복되는 시간대 패턴만 추출 |
| `day_of_week` | `tpep_pickup_datetime` | 위와 동일한 이유로, 반복되는 요일 패턴만 추출 |
| `is_airport` | `PULocationID`, `DOLocationID` | 공항(JFK/LaGuardia/Newark)이면 결제수단 구성이 확연히 다름(현금 17.4%·Flex Fare 3.2% vs 비공항 8.3%·24.3%) → 265개 구역 원-핫에 이 신호가 묻히지 않도록 이진 플래그로 직접 노출 |
| `payment_label` | `payment_type` | 정수 코드(0/1/2)를 사람이 읽을 수 있는 문자열(Flex Fare/신용카드/현금)로 매핑해 타깃을 명확히 함 |

## 3. 전체 요약 및 설계 노트

| 항목 | 값 |
|---|---|
| 원본 데이터 | `yellow_tripdata_2026-05.parquet` — **4,090,836행 × 20열** |
| dtype 구성 | float64 13개, int32 3개, datetime64 2개, str 1개, int64 1개 |
| 완전 중복 행 | **0건** (제거 불필요) |
| 결측치 있는 컬럼 | 5개, 전부 **정확히 955,371건(23.35%)로 동일** — `payment_type=0`(Flex Fare)과 100% 일치 |
| 행 필터링 후 최종 크기 | **3,891,255행** (원본 대비 95.12% 유지) |
| 최종 피처 테이블 | **3,891,255행 × 12열** (피처 11개 + 타깃 1개) |
| 타깃 클래스 분포 | 신용카드 68.36% · Flex Fare 22.57% · 현금 9.07% |
| 정제 데이터 산출물 | `payment_type_dataset.parquet` (다음 단계인 시각화·통계분석·ML Pipeline이 공통으로 사용) |

**Pandas vs Polars 사용 범위**: 2단계에서 두 라이브러리로 각각 로딩해 속도를 비교했는데(Pandas 0.23초, Polars 0.13초), 이 차이는 **디스크 I/O 단계에서만** 발생한다. 3단계 이후(EDA 집계, 중복 제거, 필터링 등)는 이미 메모리에 로딩된 데이터에 대한 연산이라 애초에 거의 즉시 끝나며(4,090,836행 기준으로도 1초 미만), Polars로 바꿔도 체감 이득이 없다. 반면 이후 단계에서 쓰는 `seaborn`·`scipy.stats`·`sklearn`은 전부 pandas DataFrame 연동을 기본으로 하므로, 로딩 이후로는 pandas로 일관되게 진행한다. (요구사항인 "Pandas·Polars 양쪽 로딩 비교" 충족)

**중복 제거는 반드시 컬럼을 줄이기 전에 한다**: 처음엔 "누수 컬럼 제외 → 중복 제거" 순서로 짰었는데, 컬럼을 10개로 줄인 뒤 중복을 검사하니 중복이 0건에서 16,306건으로 늘어나는 문제가 발견됐다. `tip_amount`·`RatecodeID` 등 세부 정보가 있을 땐 서로 다른 트립이었는데, 그 컬럼들을 지우고 나니 남은 컬럼값만 우연히 같아서 "중복"으로 잘못 잡힌 것이다. 그래서 **중복 제거(4단계)를 컬럼 제외(5단계)보다 먼저** 수행하도록 순서를 바로잡았다. 데이터프레임 이름은 `df_pandas` → `dedup_df` → `column_dropped_df` → `outlier_filtered_df` → `feature_df` 순으로 처리 단계를 따라간다.

> 관련 결정 근거는 이 문서와 `data_preparation.ipynb`에 직접 기술함.

> **스키마 변경 안전장치**: 7단계(최종 피처 테이블 구성)에서 원본에 사용/제외 목록 어디에도 없는 새 컬럼이 있으면 경고를 출력하도록 만들어 두었다. 나중에 TLC가 컬럼을 추가·변경해도 검토 없이 조용히 포함되거나 빠지지 않고, 반드시 사람이 검토하도록 하기 위함.

## 4. 다음 작업자가 검토할 부분

| 항목 | 현재 상태 | 확인할 것 |
|---|---|---|
| `cbd_congestion_fee` | 포함 | README.md는 `mta_tax`·`improvement_surcharge`와 함께 "분산≈0"으로 분류했으나, 실측 결과 34%는 \$0 / 66%는 \$0.75로 **저분산이 아님**을 확인하고 포함으로 결정함. `PULocationID`/`DOLocationID`와 정보가 얼마나 겹치는지, 포함 시 실제로 성능이 오르는지는 아직 미검증 |
| `VendorID` (V6 동어반복) | 포함 유지 | `VendorID=6`(Myle Technologies)은 100% Flex Fare(7,643건, 전체 Flex Fare의 0.8%)라 동어반복 위험 있음. 전체 성능에 영향은 작을 것으로 판단해 유지했으나, V6 제외 후 재학습해서 성능 차이가 없는지 사후 검증 권장 |
| 팁 비율 77%인 지역 | 미확인 | README.md에 "특정 지역 팁 비율 0~77.2%"로 언급되었으나 원인(지역 코드) 미확인. 지역 코드 매핑 테이블로 대조 필요 |
| `hour` 순환 인코딩 | 미반영 (정수 그대로 원-핫) | README.md "예측 힌트" 표: "시간은 순환값(23시→0시가 인접)이므로 인코딩 방식 검토 필요"라고 명시됨. 현재는 `hour`를 0~23 정수로 두고 범주형 원-핫 인코딩만 적용 — 원-핫은 각 시간을 독립 카테고리로 취급해 순환성 문제 자체는 우회하지만, README가 제안한 `sin`/`cos` 변환과는 다른 접근. 두 방식의 모델 성능 차이 비교 필요 |
| `trip_distance`, `fare_amount` 로그 변환 | 미반영 | README.md "분포" 표: `trip_distance`는 skew **386**, `fare_amount`는 skew **22**로 우측으로 크게 치우쳐 있고, `log1p` 적용 시 정규분포에 가까워진다고 명시됨 — 둘 다 **로그 변환**이 제안됨. 현재 `data_preparation.ipynb`는 이상치 제거만 하고 로그 변환 컬럼은 만들지 않음. |
| `PULocationID`/`DOLocationID` 원-핫 유지 여부 | `is_airport` 추가, 원본 컬럼도 유지 | `is_airport`가 공항 신호를 명시적으로 뽑아냈지만, `PULocationID`/`DOLocationID` 265개 구역 원-핫은 그대로 남아 있음. 나머지 구역 간 차이(예: East Village Flex Fare 36.8%)도 신호가 있어 일단 유지했으나, 모델링 단계에서 원-핫 희소성이 문제되면 `is_airport` 등 소수 파생 피처로 대체하는 걸 검토할 것 |
