# Step 2 — 전처리 결과

- 원본: 4,090,836행 × 20컬럼
- 정제 후: **3,891,795행 × 25컬럼** (원본의 95.1%)

> 이 단계는 데이터를 바꾸는 유일한 단계다. 탐색·통계·시각화는 Step 3·4·5에서 한다.

## 1. 정제 전 현황

중복 행은 **0건**으로 제거할 것이 없다.

결측이 있는 컬럼은 아래 5개이며, 모두 정확히 같은 건수다.

| 컬럼 | 결측건수 |
|---|---|
| passenger_count | 955,371 |
| RatecodeID | 955,371 |
| store_and_fwd_flag | 955,371 |
| congestion_surcharge | 955,371 |
| Airport_fee | 955,371 |

**이 결측 행이 전부 `payment_type=0`(Flex Fare)인지 교차 검증한 결과: 일치함.**
따라서 이는 무작위 결측이 아니라, Flex Fare가 앱 기반 사전 확정요금이라
미터기 세부 요금 필드가 **애초에 해당 없음**을 의미한다. 채우거나 지울 대상이 아니다.

## 2. 정제 내역

### 2-1. 분석 대상 선별
`payment_type` 3(무료)·4(분쟁)를 제외했다. 합산 34,971건으로
표본이 지나치게 적어 신뢰할 수 있는 분류가 불가능하다.

### 2-2. 이상값 제거 (규칙별 해당 건수)

| 규칙 | 해당건수 | 비율% |
|---|---|---|
| 요금 ≤ 0 | 6,087 | 0.15 |
| 이동거리 ≤ 0 | 107,168 | 2.642 |
| 이동거리 > 200마일 | 73 | 0.002 |
| 소요시간 ≤ 0분 | 51,367 | 1.266 |
| 소요시간 > 180분 | 1,404 | 0.035 |

> 규칙끼리 겹칠 수 있으므로 위 합계와 실제 제거 건수는 다르다.
> 대상 선별 후 4,055,865행 → 이상값 제거 후 **3,891,795행**

### 2-3. 생성한 파생변수

| 변수 | 내용 | 만든 이유 |
|---|---|---|
| `trip_duration_min` | 하차 − 승차 (분) | 원본에 소요시간이 없다 |
| `pickup_hour` | 승차 시각의 '시' (0~23) | 시간대별 패턴을 보기 위해 |
| `day_of_week` | 요일 (월=1 … 일=7) | 평일과 주말의 이동 성격이 다르다 |
| `is_weekend` | 주말 여부 | 위와 동일, 이진 피처로 |
| `payment_label` | 결제수단 이름 | 0/1/2 코드를 읽을 수 있게 |

## 4. 저장 파일에 남은 결측 — 결함이 아님

`cleaned.parquet`에는 결측이 **4,391,275개** 남아 있다.
이는 Flex Fare 878,255행 × 5개 컬럼과
정확히 일치하며, 그 외 행의 결측은 0이다.

채우거나 지우지 않고 그대로 두는 이유는 **값이 없는 것이 아니라 항목 자체가 해당 없기 때문**이다.
평균으로 채우면 존재하지 않는 미터기 요금을 지어내는 셈이 된다.

### 모델 피처에서 제외할 누수 컬럼 7개

`tip_amount`, `total_amount`, `congestion_surcharge`, `Airport_fee`, `RatecodeID`, `passenger_count`, `store_and_fwd_flag`

앞의 두 개는 팁 정보라 결제수단을 그대로 노출하고, 나머지는 Flex Fare에서만 비어 있어
"비어 있으면 Flex Fare"라는 규칙을 외우게 만든다.
**Step 3이 이를 근거로 피처 화이트리스트(`features.json`)를 확정하고, Step 6은 그 목록만 사용한다.**
