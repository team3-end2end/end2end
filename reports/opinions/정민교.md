# 본인 의견 — 정민교 (결과 해석·통합)

> 아래 「사실 정리」는 확인용입니다. 「느낀 점」·「개선하고 싶은 부분」은 초안이니 본인 문장으로 고쳐 쓰세요.

## 사실 정리 — 내가 한 것

각자 만든 부분을 하나로 잇고, 나온 수치가 무엇을 뜻하는지 해석하는 일을 담당했다.

- **실측값 연결**: 학습 결과(모델 파일·`results.csv`·실행 로그)를 보고서 입력 JSON 5개로 옮겨 `report.md` / `report.html`을 실제 수치로 생성했다. 혼동행렬에서 지표를 역산해 기록값과 소수점 6자리까지 일치하는지 검증했다.
- **결과 해석 작성** (`reports/final_report.md`): XGBoost·HistGBM·로지스틱 세 모델이 왜 그런 점수를 냈는지, 비유를 쓰되 사실을 왜곡하지 않는 선에서 정리했다.
- **모델 저장 검증 추가**: 저장한 joblib을 다시 읽어 예측이 일치하는지 확인하는 `verify_saved_model()`을 파이프라인에 넣었다. "저장했다"는 로그를 믿지 않고 확인하도록.
- **보고서에 Pandas/Polars 비교 추가**: 노트북에만 있던 로딩 비교를 보고서 스키마에 선택 필드로 넣고, 템플릿·검증·테스트까지 붙였다.
- **단일 진입점** (`main.py`): 흩어져 있던 실행 명령을 하나로 묶었다. 기본 모드는 저장된 결과를 재사용하고, `--full`은 학습부터 전체를 돌린다. 마지막에 산출물 11개의 존재와 크기를 코드가 확인한다.
- **문서 정비**: README(목적·환경·실행법·데이터 출처·산출물·팀 역할), requirements 버전 명시, 제출용 HTML 빌드 스크립트.

## 핵심 결정과 근거

**자동 생성물과 사람이 쓴 문서를 분리한 것**이 가장 중요한 결정이었다. `report.md`는 코드가 만든 수치만 담고 손대지 않았고, 해석은 `reports/final_report.md`에 따로 썼다. 이렇게 하지 않으면 보고서를 다시 생성할 때마다 해석이 날아가고, "이 숫자가 진짜 실행 결과인가"를 보장할 수 없다.

또 하나는 **해석을 검증 가능한 형태로 쓴 것**이다. "현금 예측이 나쁘다"로 끝내지 않고 혼동행렬에서 오분류가 어디서 나오는지(카드 53만 중 14만 건이 현금으로) 짚었고, 통계 검정 결과(효과크기 |d| ≤ 0.11)와 대조해 같은 결론에 도달하는지 확인했다.

## 느낀 점 (초안 — 본인 문장으로 고쳐 쓸 것)

정확도 74.3%라는 숫자 자체보다 **모델이 왜 틀리는지를 특정한 것**이 이번 작업에서 가장 의미 있었다. 처음에는 성능이 낮으니 튜닝을 더 해야 하나 생각했는데, 혼동행렬을 뜯어보니 오분류가 카드↔현금 한 쌍에 몰려 있었고 플렉스 페어는 F1 0.93으로 거의 완벽했다. 통계 검정도 같은 곳을 가리켰다. 결국 문제는 알고리즘이 아니라 **데이터에 카드와 현금을 가를 신호가 없다**는 것이었고, 이건 모델을 아무리 바꿔도 넘을 수 없는 벽이었다.

여러 사람이 만든 결과를 하나로 잇는 일도 생각보다 까다로웠다. 각자 다른 방식으로 수치를 남겨서(로그·CSV·노트북 출력) 이걸 대조하는 데 시간이 들었다. 형식을 먼저 정해두면 이 비용이 사라진다는 걸, 보고서 시스템의 JSON 계약이 실제로 작동하는 걸 보면서 이해했다.

## 개선하고 싶은 부분 (초안)

- **파이프라인에서 보고서까지 자동으로 잇지 못했다.** 학습 결과를 JSON으로 옮기는 마지막 한 칸이 수동이라, "손으로 숫자를 옮길 여지가 없어야 한다"는 원칙이 절반만 지켜졌다. 평가 함수가 클래스별 지표를 반환하도록 고치면 연결된다.
- **개선안을 검증하지 못했다.** 승차지역별 현금 비율 피처를 추가하면 나아질 것이라는 가설을 세웠지만, 실제로 넣어 성능이 오르는지는 확인하지 못했다. 예측 임계값 조정은 재학습 없이 가능해서 시간만 있었다면 시도할 수 있었다.
- **데이터를 저장소에 포함시켰다.** 원칙상 다운로드 스크립트로 대체해야 하지만(80MB), 제출 방식이 "GitHub에서 받아 압축"이라 데이터가 없으면 채점자가 실행할 수 없다. 재현성을 우선해 포함했고 실무라면 분리하는 것이 맞다.
- **팀 작업 범위를 늦게 파악했다.** 다른 사람이 이미 만든 것(예: 로딩 비교)을 나중에 발견해 중복이 생겼다. 초반에 서로 무엇을 만들고 있는지 공유했다면 줄일 수 있었다.
